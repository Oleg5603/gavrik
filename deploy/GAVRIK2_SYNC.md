# Гаврик 2: безопасная синхронизация VPS и ПК

## Назначение

GitHub является единственным источником **кода**. Рабочий VPS остаётся активным
узлом, а Гаврик 2 на ПК — тёплым резервом. Оба узла получают один явно заданный
Git ref и никогда не отправляют изменения из сценариев синхронизации.

Синхронизация не означает автоматическое переключение роли. Сценарии только
получают код, создают изолированное окружение, устанавливают зависимости,
запускают тесты и записывают подтверждённый SHA. Telegram на резервном ПК они не
запускают.

## Обязательная инвентаризация действующего VPS

До заявления о «точной копии» с сервера нужно снять и проверить живой манифест:

- дистрибутив, архитектуру, Python и системные пакеты;
- URL Git remote, ветку/ref и текущий commit SHA;
- unit-файл systemd, рабочий каталог, пользователя и политику рестарта;
- перечень имён переменных окружения без их значений;
- внешние службы, расписания, сетевые порты и каталоги постоянных данных;
- версии Python-зависимостей и результат полного набора тестов;
- резервное копирование и процедуру восстановления состояния.

Без этого манифеста Гаврик 2 считается подготовленным резервом, но не доказанной
точной копией сервера.

## Что синхронизируется

- отслеживаемый Git-код и конфигурационные шаблоны;
- выбранный неизменяемый commit, tag или remote-tracking ref;
- зависимости из отслеживаемого `requirements.txt`;
- запись последнего SHA, прошедшего тесты на конкретном узле.

## Что не синхронизируется через Git

- `.env`, ключи, учётные данные и локальные настройки доступа;
- журналы, lock-файлы, PID-файлы, сессии и очереди;
- пользовательские данные, выгрузки лидов и резервные копии;
- виртуальные окружения, кэши и сгенерированные артефакты.

Эти данные переносятся отдельным утверждённым процессом: секреты — через
локальное защищённое хранилище, состояние — через проверяемую резервную копию.
Сценарии ниже намеренно не копируют их между машинами.

## Модель обновления

1. Оператор выбирает Ref (лучше полный commit SHA или подписанный tag).
2. На резервном ПК запускается `deploy/windows/sync_gavrik2.ps1`.
3. Сценарий прекращает работу при грязном Git-дереве, ошибке fetch, установки
   зависимостей или тестов.
4. Код переводится в detached HEAD на проверяемый commit без `reset --hard`.
5. Только после успешных тестов SHA записывается во внешний state-файл.
6. Telegram остаётся выключенным до отдельного ручного переключения роли.
7. После проверки резерва тем же Ref можно обновить VPS через
   `deploy/linux/sync_gavrik_server.sh` в отдельное окно обслуживания.

## Fencing при переключении

Одновременно активен только один получатель Telegram updates. Перед включением
Гаврика 2 оператор обязан:

1. остановить и проверить остановку systemd-службы на VPS;
2. убедиться, что на VPS отсутствует процесс приложения и автоматический restart;
3. зафиксировать роль владельца в доступном обоим узлам внешнем lease/lock либо
   выполнить документированный ручной контроль;
4. только затем отдельно запустить приложение на ПК;
5. при возврате на VPS сначала остановить ПК и проверить отсутствие процесса.

Потеря связи с одним узлом не является разрешением автоматически запускать
второй. Если нельзя доказать, что прежний лидер остановлен, переключение
запрещено: это защищает от двух одновременно работающих экземпляров.

## Примеры

ПК (PowerShell):

```powershell
.\deploy\windows\sync_gavrik2.ps1 -RepoPath C:\gavrik2 -Ref origin/main
```

VPS (из окна обслуживания; подтверждённый каталог сервера):

```bash
./deploy/linux/sync_gavrik_server.sh /home/vpsadmin/gavrik origin/master /home/vpsadmin/gavrik/.sync-venv /home/vpsadmin/.local/state/gavrik/applied-sha
```

Оба сценария являются pull-only. Публикация изменений выполняется только
обычным проверяемым процессом разработки, не действующим сервером и не резервом.
